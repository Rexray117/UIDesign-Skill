# 工作流：五道闸门

从「用户说要一个界面」到「可交付的界面」，必须依次通过五道闸门。
**跳过任何一道，都会以可预测的方式制造 AI 味**——下表末尾列出了每种跳闸的后果。

---

## 闸门总览

| 闸门 | 一句话任务 | 交付物 | 跳过后的后果 |
|------|-----------|--------|-------------|
| G0 场景识别 | 这是哪类界面？ | 场景判定 + 技术栈确认 | 用营销页的逻辑做监控界面，密度与对比全部错位 |
| G1 设计主张 | 它主张什么？ | 一份可被反驳的立场 | **滑向训练数据的安全中心——AI 味的主因** |
| G2 风格选型 | 用什么视觉语言表达这个立场？ | 1 主风格 + ≤1 辅风格 + token 处方 | 风格与立场脱节，装饰与内容打架 |
| G3 构建 | 用手艺把它做出来 | 代码 / 设计稿 + 完整状态 | 硬编码色值，无法切换主题，状态缺失 |
| G4 去 AI 味 + 验证 | 它真的落地了吗？ | 自检报告 + 交付清单 | **永远不知道自己交付了什么** |

---

## G0 · 场景识别

### 动作

1. **判定场景**。对照 `SKILL.md` 的场景路由表，在六类中选定一类。
   - 歧义时按「**主要使用者的首要目标**」判定，而不是按页面长相。
     例：一个内部工单系统长得像 SaaS 前台，但它服务的是「批量处理与一致性」，所以属于**管理界面**。
2. **确认技术栈**。检查 `package.json`（react/vue/svelte/@angular）、`pubspec.yaml`（Flutter）、`*.xcodeproj`（SwiftUI）、`composer.json`（Laravel）、`app.json` + `react-native`（RN）。
3. **确认既有约束**：品牌色、既有字体、既有组件库、既有设计规范、无障碍等级要求。

### 禁止

- **不要假设技术栈。** 假设错了会让后续所有实现建议错位。
- **不要在信息不足时静默选默认值。** 栈无法探测且会影响实现时，直接问用户。

### 产出

```
场景：企业监控界面
栈：React 18 + Vite + Tailwind + ECharts（已探测）
既有约束：品牌主色 #0F3D5C；要求 WCAG AA；已有 antd 5 组件库
```

## G1 · 设计主张（最容易被跳过、也最致命）

### 动作

填写 `assets/templates/design-brief.md`，回答四问。**四问都必须有具体答案，不接受「现代简洁」这类词。**

| 四问 | 要求 | 不合格 | 合格 |
|------|------|--------|------|
| **目的** | 谁在什么情境下用它完成什么 | 「给用户看数据」 | 「夜班运维在 3 秒内判断 200 台设备里哪台要炸」 |
| **调性** | 一个**单一**的调性词，且能被反驳 | 「现代、简洁、专业」 | 「仪表盘式的冷静——像飞机驾驶舱，不像展厅」 |
| **约束** | 技术上或业务上真正的限制 | 「要好看」 | 「必须能塞进 1440×900 无横向滚动；只有 1 个开发重复用组件」 |
| **差异化** | **一个**标志性元素，其余克制 | 「哪哪都不一样」 | 「只有告警数字用等宽超大字号，其它一律安静」 |

### 为什么四问能治 AI 味

AI 味的定义是「没有立场的通用感」。**四问强制产出一个立场。**
- 「调性」只有一个词 → 迫使取舍
- 「差异化」只有一个元素 → 阻止全身都是重点
- 「目的」必须带情境 → 阻止设计脱离使用现场

### 反面模式（明确拒绝这些默认答案）

- ❌ 米色 + 衬线体（AI 生成的「高级感」默认套餐）
- ❌ 酸性色 on 纯黑（AI 生成的「赛博感」默认套餐）
- ❌ 紫→粉渐变（AI 生成的「科技感」默认套餐）
- ❌ 三等分卡片 + 大圆角 + 柔和阴影（AI 生成的「现代感」默认套餐）

**如果四问的答案指向了上面任何一个，重答一遍。**

## G2 · 风格选型

### 动作

1. 打开 `references/styles/index.md` 的**场景适配矩阵**，把「适配度为高」的风格列为候选。
2. 读 `references/styles/prescriptions.md` 中候选风格的完整处方。
3. **选定 1 个主风格，最多 1 个辅风格。** 辅风格只允许在明确的位置使用（如「主风格 Swiss，仅数据区用 Data-Dense」）。
4. 用三旋钮定调：`--variance`（非对称度）/ `--motion`（动效强度）/ `--density`（信息密度），各取 1–10。
5. 把决策写进 `assets/templates/style-decision.md`，包含**被否决的候选及理由**。

### 判定标准

一个风格选得对不对，只看一条：**它的「差异化抓手」是否正好服务于 G1 的「目的」。**
如果不是，换一个风格，而不是加装饰去硬凑。

### 禁止

- ❌ 混搭两个以上风格（除非有明确的分区理由）
- ❌ 选一个「安全」风格然后靠装饰找补
- ❌ 在没读处方的情况下凭印象使用某风格（处方里的「AI 味陷阱」是必备项）

## G3 · 构建

### 动作

0. **先取用，再自造。** 打开 `references/scenario-templates.md`，看 `assets/scenario-templates/`
   里是否已有可复用的组件（约 4,100 行已验证代码，覆盖 6 个场景）。该目录经本技能自检脚本
   审计得 **2.9/100（A 档）**——即模板自身遵守了本技能的全部规则。有就改，没有才写。
1. **先建 token，再写组件。** 按 `references/foundations/tokens.md` 的三层结构建 `primitives` / `semantic` / `components`。
   起步可直接改用 `assets/design-tokens.starter.json`，或直接用 `assets/scenario-templates/tokens.css`。
2. 排版与色彩按 `references/foundations/typography-color.md`。
3. 布局、栅格、间距按 `references/foundations/layout-grid.md`。
4. 组件实现按 `references/foundations/components-states.md`——**六态必须齐全**（default / hover / focus / active / disabled / loading）。
5. 动效按 `references/foundations/motion.md`。
6. 若含图表，按 `references/quality/charts.md` 选型；**系列色从 token 层读取，不在组件里写 hex**。

### 硬性纪律

- **禁止组件内出现裸 hex 色值。** 一律引用语义 token。
- **禁止魔法数字间距。** 一律走间距尺度。
- **禁止 emoji 当图标。** 用 SVG 图标族（Lucide / Heroicons / Phosphor），且全站同一族同一线宽。
- **一致性优先于局部最优。** 新写法要么统一推广，要么不用。

### 产出

可运行的界面 + 一份 token 文件。**此时不要声称「已完成」**——G4 还没跑。

## G4 · 去 AI 味 + 验证

### 动作 1：跑诊断

```bash
python scripts/ai_flavor_audit.py <产出目录或文件> [--json] [--scenario admin]
```

读 `references/anti-ai/diagnosis.md` 理解六维含义与评分。**重点看分数，更看清单**——脚本指出的具体位置比总分有用。

### 动作 2：对照处方改造

按 `references/anti-ai/fixes.md` 中对应维度的处方逐项改。优先级：

1. **语义层（内容与文案）** —— 收益最大，见 `references/anti-ai/copy-tells.md`
2. **结构层（布局与信息架构）** —— 收益次大
3. **视觉层（色彩、排版、装饰）** —— 收益可见但上限低
4. **动效层** —— 收尾

### 动作 3：误杀检查（强制，不可跳过）

过一遍 `references/anti-ai/false-positives.md`。**逐条确认自己的改动没有砍掉设计纪律。**

三个最常见的误杀：
- 把「高信息密度」当 AI 味砍掉 → 毁了监控界面
- 把「一致性重复」当 AI 味砍掉 → 毁了管理界面的可预测性
- 把「完整的状态设计」当 AI 味砍掉 → 毁了可用性

### 动作 4：质量闸

1. `references/quality/accessibility.md` —— 对比度、焦点、键盘、aria
2. `references/quality/ux-rules.md` —— 十类优先级规则
3. `references/quality/delivery-checklist.md` —— 逐项打勾

### 动作 5：真看一遍

**在真浏览器里打开，截 375 / 768 / 1024 / 1440 四档，并切到暗色模式看一次。**
只读代码不算验证。这一步能抓到代码评审抓不到的东西：焦点环丢了、窄屏下徽标压到卡片边框、数字在卡片滚入视野前就动完了。

### 迭代上限

改造循环**最多 3 轮**。超过 3 轮仍不达标，说明问题在 G1 或 G2——**回到上游改立场或改风格，而不是继续磨视觉层**。

---

## 闸门间的回退规则

| 症状 | 该回退到 |
|------|----------|
| 越改越花、重点全散 | G1（差异化没收敛到单一元素） |
| 视觉没问题但「就是不对」 | G2（风格与目的不匹配） |
| 每改一次都引入新的不一致 | G3（token 没建好，在打补丁） |
| 脚本分数上不去 | G1/G2，而不是继续加改造动作 |
| 用户说不出哪里不对 | G0（场景判定错了） |
